SLIP-48
=======

Panes
-----

`draft` `optional` `author:melvincarvalho`

| Status | Implemented in JSS |
|--------|-------------------|
| Draft  | N/A (client-side) |

This SLIP defines panes — small ES modules that render a single linked-data subject — and the `urn:solid:view` predicate that lets a TypeRegistration declare which pane to use.

## Overview

Apps that walk a user's [Type Index](./43.md) discover *where* their data lives. A pane decides *how* one of those resources is shown. The convention originated with [mashlib](https://github.com/solid/mashlib) / [SolidOS](https://github.com/SolidOS) and is formalised here so panes can be authored, discovered, and shared independently of any single host.

A pane is:

- **an ES module** with a known interface (below)
- **registered with a host** (statically by the app, or dynamically via `urn:solid:view` on a pod)
- **portable** across hosts — any client implementing this SLIP loads the same pane

## Pane Interface

A pane is an ES module whose `default` export is a plain object exposing four members:

```js
export const label = 'Tasks'
export const icon  = '✅'

export function canHandle(subject, store) { /* boolean */ }
export function render(subject, store, container, rawData) { /* emit DOM */ }

export default { label, icon, canHandle, render }
```

| Member | Type | Description |
|--------|------|-------------|
| `label` | string | Human-readable name shown in pane pickers and tabs. |
| `icon` | string | Emoji or short glyph identifying the pane. |
| `canHandle(subject, store)` | function → boolean | Does this pane render the given subject? |
| `render(subject, store, container, rawData)` | function | Emit DOM into `container` representing `subject`. |
| `default` | object | An aggregate of the four above, so a pane can be loaded as a single value. |

The named exports and the `default` export carry the same information; hosts MAY load whichever fits their machinery.

## Subject and Store

`canHandle` and `render` receive an rdflib-shaped `subject` and `store`:

| Argument | Description |
|----------|-------------|
| `subject` | An rdflib [`NamedNode`](https://github.com/linkeddata/rdflib.js) — `{ value, termType }`. `value` is the resource's URL (with any fragment). `termType` is `"NamedNode"` for a real subject, `"BlankNode"` for inline subjects. |
| `store` | An rdflib [`Store`](https://github.com/linkeddata/rdflib.js). Panes use `store.statementsMatching(subject, predicate, object)` to read RDF triples about the subject. Each statement has `.predicate.value`, `.object.value`, `.object.termType`. |

`store` MAY include any data the host has loaded — typically the full document referenced by `subject`, plus related resources (linked profiles, type indexes, friend lists). Panes SHOULD only walk what they need.

## The `rawData` Parameter

`render`'s fourth argument is an optional pre-parsed JSON-LD payload:

```js
render(subject, store, container, rawData)
```

If the host has the original document already (as JSON-LD), it MAY pass it as `rawData`. Panes MAY use it instead of `store` to avoid re-parsing. When `rawData` is absent, panes fall back to `store.statementsMatching(...)`.

## Loading Panes in a Host

Two common patterns:

**1. `<script type="module" data-pane>` (mashlib-style).** The host scans the document for `data-pane` script tags, dynamically imports each one, and registers the default export.

```html
<script type="module" data-pane src="https://solid-apps.github.io/pilot/tracker-pane.js"></script>
```

**2. Direct ES import.** Apps wishing to ship a pane statically import its named or default exports.

```js
import * as TrackerPane from './panes/tracker.js'
register(TrackerPane.default ?? TrackerPane)
```

## Registration on a Pod

A TypeRegistration MAY include `urn:solid:view` ([term](https://urn-solid.com/view/), `owl:sameAs http://w3id.org/solidos#view`) pointing at the ES module that should render its instances:

```jsonld
{
  "@context": {
    "solid": "http://www.w3.org/ns/solid/terms#",
    "view":  "urn:solid:view"
  },
  "@id": "#reg-tracker",
  "@type": "solid:TypeRegistration",
  "solid:forClass": { "@id": "http://www.w3.org/2005/01/wf/flow#Tracker" },
  "solid:instance": { "@id": "/public/tracker/work-data.jsonld#this" },
  "view":           { "@id": "https://solid-apps.github.io/pilot/tracker-pane.js" }
}
```

Hosts SHOULD read all three accepted forms of the predicate:

| Form | Notes |
|------|-------|
| `urn:solid:view` | Canonical (urn-solid registry). |
| `http://w3id.org/solidos#view` | `owl:sameAs` of the canonical. |
| `view` | Bare key, when aliased in `@context`. |

Since the choice lives on the pod, it travels across browsers and is honoured by any client that implements this SLIP.

## Resolution Order

When a host has discovered a subject and needs to render it, it MUST resolve a pane in this order:

1. **`urn:solid:view`** on the TypeRegistration. The host loads the module; if its `canHandle` accepts the subject, use it.
2. **User-pinned default** for the subject's class (if the host supports per-class defaults).
3. **First registered pane whose `canHandle` returns true**, in registration order.

If none match, the host SHOULD render a clear "no pane available" placeholder rather than fall through silently.

## Discovery and Trust

`urn:solid:view` is a URL that the host imports as code. Hosts MUST treat it like any other untrusted import:

- Confirm before loading URLs from origins outside an allow-list (the pod's own origin is a reasonable default).
- Cache loads per-URL; don't re-import on every render.
- Surface load failures (network, CORS, parse) to the user — don't let a broken pane silently fall back to a different one without notice.

A pane that loads gets full DOM and full pod-write access (via the host's authenticated `fetch`). Authoring conventions, signing, and sandboxing are out of scope for this SLIP.

## Example

A complete LOSOS-style pane:

```js
// hello-pane.js
const SCHEMA = 'http://schema.org/'

export const label = 'Hello'
export const icon  = '👋'

export function canHandle(subject, store) {
  if (subject.termType !== 'NamedNode') return false
  const RDF_TYPE = 'http://www.w3.org/1999/02/22-rdf-syntax-ns#type'
  return store.statementsMatching(subject, undefined, undefined)
    .some(s => s.predicate.value === RDF_TYPE && s.object.value === SCHEMA + 'Person')
}

export function render(subject, store, container) {
  const stmts = store.statementsMatching(subject, undefined, undefined)
  const name = stmts.find(s => s.predicate.value.endsWith('name'))?.object.value
  container.innerHTML = `<h1>Hello, ${name ?? '(unnamed)'}</h1>`
}

export default { label, icon, canHandle, render }
```

Pin it on the pod:

```jsonld
{
  "@context": {
    "solid": "http://www.w3.org/ns/solid/terms#",
    "view":  "urn:solid:view"
  },
  "@id": "#reg-people",
  "@type": "solid:TypeRegistration",
  "solid:forClass": { "@id": "http://schema.org/Person" },
  "solid:instanceContainer": { "@id": "/people/" },
  "view": { "@id": "https://example.org/hello-pane.js" }
}
```

Any host implementing this SLIP — mashlib, hub, a future client — will load the same pane and render Person resources the same way.
