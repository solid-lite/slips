SLIP-34
=======

urn:solid Vocabulary
--------------------

`draft` `optional` `author:melvincarvalho`

| Status | Implemented in JSS |
|--------|-------------------|
| Draft  | N/A (vocabulary) |

This SLIP defines the `urn:solid:` namespace — a curated, vocabulary-agnostic registry of RDF terms — and the canonical resolution and consumption patterns for it.

## Overview

Solid apps mix RDF from many vocabularies: FOAF for people, Schema.org for events, vcard for contacts, ActivityStreams for activities, dcterms for metadata, ldp for containers. Different apps pick different prefixes for the same concept. This makes interop painful: a pane that handles `foaf:Person` won't see data tagged `schema:Person` even though they describe the same thing.

`urn:solid:` is an indirection layer. Every term is a stable `urn:solid:<Name>` identifier with an `owl:sameAs` pointing at the canonical equivalent in an established vocabulary. Apps can register against `urn:solid:Person` and match data regardless of which upstream prefix the source app used.

The registry lives at <https://urn-solid.com> ([source](https://github.com/urn-solid/urn-solid.github.io)).

## The Namespace

The namespace prefix is `urn:solid:`. It conforms to [RFC 8141](https://tools.ietf.org/html/rfc8141) (URN syntax).

Naming conventions:

| Kind | Case | Example |
|------|------|---------|
| Class | PascalCase | `urn:solid:Person`, `urn:solid:Tracker` |
| Property | camelCase | `urn:solid:name`, `urn:solid:storage`, `urn:solid:view` |

Names are case-sensitive per RFC 8141; `urn:solid:Person` and `urn:solid:person` are distinct terms.

## Term Shape

Each term is a JSON-LD document conforming to the [registry schema](https://urn-solid.com/schema/term.schema.json):

```jsonld
{
  "@context": "https://urn-solid.com/context.jsonld",
  "@id": "urn:solid:Person",
  "@type": "rdfs:Class",
  "rdfs:label": "Person",
  "rdfs:comment": "A human being.",
  "owl:sameAs": "http://xmlns.com/foaf/0.1/Person",
  "rdfs:seeAlso": ["https://schema.org/Person"],
  "status": "stable",
  "added": "2026-04-18"
}
```

Required fields:

| Field | Type | Description |
|-------|------|-------------|
| `@context` | string | Always `https://urn-solid.com/context.jsonld`. |
| `@id` | string | The `urn:solid:<Name>` identifier. |
| `@type` | enum | `rdfs:Class` or `rdf:Property`. |
| `rdfs:label` | string | Short human-readable name (≤ 80 chars). |
| `rdfs:comment` | string | One-sentence definition (≤ 280 chars). |
| `status` | string | `draft` \| `stable` \| `deprecated`. |
| `added` | date | ISO date the term was first published. |

Optional fields cover semantics (`owl:sameAs`, `rdfs:seeAlso`, `rdfs:domain`, `rdfs:range`), guidance (`notes`, `notToBeConfusedWith`, `supersededBy`), provenance (`provenance`, `history`), and authoring aids (`examples` — embedded JSON-LD samples).

## Endpoints

The registry exposes a small, predictable set of canonical URLs:

| URL | Purpose |
|-----|---------|
| `https://urn-solid.com/<Name>/` | HTML page for one term, with the JSON-LD inlined as a [data island](./32.md). |
| `https://urn-solid.com/<Name>/index.json` | Raw JSON-LD for one term. |
| `https://urn-solid.com/corpus.jsonl` | All terms, one JSON-LD object per line. |
| `https://urn-solid.com/index.json` | Label-keyed index for fast lookup. |
| `https://urn-solid.com/context.jsonld` | Canonical `@context` mapping standard prefixes (foaf, schema, vcard, dcterms, as, prov, ldp, solid, urns) for use in any urn:solid document. |
| `https://urn-solid.com/schema/term.schema.json` | JSON Schema (Draft 2020-12) the term files conform to. |
| `https://urn-solid.com/llms.txt` | LLM-oriented usage guide. |
| `https://urn-solid.com/SKILL.md` | Agent skill describing how to use the registry. |

Clients SHOULD fetch `corpus.jsonl` once and cache it; per-term pages are useful for human readers and for data-island embedding in pages that display a single term.

## Resolving Terms

Every term `urn:solid:<Name>` resolves to a real, fetchable URL:

```
urn:solid:Person  →  https://urn-solid.com/Person/
urn:solid:view    →  https://urn-solid.com/view/
```

Fetching the URL returns HTML with the term's JSON-LD inlined; appending `index.json` returns the raw JSON-LD. This makes the URN both a stable identifier (for use in JSON-LD `@id`) and a dereferenceable URL (for a client that wants to look up the term).

## Using Terms in Apps

Three common patterns:

**1. Use the urn:solid context in your data.**

```jsonld
{
  "@context": "https://urn-solid.com/context.jsonld",
  "@id": "https://alice.example.org/profile#me",
  "@type": "urn:solid:Person",
  "urn:solid:name": "Alice"
}
```

**2. Alias terms for readability.**

```jsonld
{
  "@context": {
    "urns": "urn:solid:vocab/",
    "view":  { "@id": "urn:solid:view", "@type": "@id" }
  },
  "@id": "#reg-tracker",
  "@type": "solid:TypeRegistration",
  "view":  { "@id": "https://example.org/tracker-pane.js" }
}
```

**3. Match foreign IRIs against urn:solid in code.**

```js
// Build a map from corpus.jsonl
const corpus = await fetch('https://urn-solid.com/corpus.jsonl').then(r => r.text())
const byCanonical = {}
for (const line of corpus.split('\n').filter(Boolean)) {
  const t = JSON.parse(line)
  const sameAs = [].concat(t['owl:sameAs'] ?? [])
  for (const iri of sameAs) byCanonical[iri] = t['@id']
}

// e.g. byCanonical['http://xmlns.com/foaf/0.1/Person'] === 'urn:solid:Person'
```

A pane (see [SLIP-48](./48.md)) that wants to handle "any kind of person" tests both the urn:solid term and its `owl:sameAs` partners; or maps every incoming IRI to its `urn:solid:` form first and matches on that.

## Adding and Updating Terms

The registry is curated. To propose a new term:

1. Search `corpus.jsonl` for an existing term that already covers your concept.
2. If none exists, open an issue at <https://github.com/urn-solid/urn-solid.github.io/issues> with:
   - the proposed name (PascalCase for class, camelCase for property),
   - a one-sentence definition,
   - the canonical IRI in an established vocabulary (for `owl:sameAs`),
   - one example use.
3. Term files validate against the JSON Schema; status starts at `draft`, promoted to `stable` once used in the wild and reviewed.

Deprecation uses `status: "deprecated"` plus `supersededBy` pointing at the replacement; nothing is ever removed.

## Example: Pane Discovery via urn:solid

Combining this SLIP with [SLIP-43](./43.md) (Type Index) and [SLIP-48](./48.md) (Panes):

```jsonld
{
  "@context": {
    "solid": "http://www.w3.org/ns/solid/terms#",
    "view":  "urn:solid:view"
  },
  "@id": "#reg-people",
  "@type": "solid:TypeRegistration",
  "solid:forClass": { "@id": "urn:solid:Person" },
  "solid:instanceContainer": { "@id": "/people/" },
  "view": { "@id": "https://example.org/person-pane.js" }
}
```

A host that resolves `urn:solid:Person` via the registry sees `owl:sameAs http://xmlns.com/foaf/0.1/Person` and matches data tagged either way. The `urn:solid:view` predicate (itself a registry term) declares the renderer.
